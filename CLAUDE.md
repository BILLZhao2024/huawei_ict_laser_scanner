# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Overview

STM32F401CCU6 firmware for interfacing with a **DAC8563** DAC chip via SPI1. Generated by STM32CubeMX v6.17.0 using STM32Cube FW_F4 V1.28.3 HAL. Uses a custom `setup()`/`loop()` application pattern similar to Arduino, layered over the standard HAL.

## Build & Flash

Built with **Keil MDK-ARM V5** (ARM Compiler 5). No CLI build tools (no Makefile, CMake, or gcc).

- **Project file:** `MDK-ARM/stm32f401ccu6.uvprojx`
- **Device pack:** Keil.STM32F4xx_DFP.3.1.1
- **Preprocessor defines:** `USE_HAL_DRIVER, STM32F401xC`
- **CPU:** Cortex-M4, 256 KB Flash (`0x08000000`), 64 KB RAM (`0x20000000`)
- **Compiler:** ARMCC V5.06 update 7 (build 960), C99 mode, optimization level 1
- **Output:** `MDK-ARM/stm32f401ccu6/stm32f401ccu6.hex` (hex file generation enabled)
- **Debug probe:** J-Link (via `JLinkSettings.ini`)

Build from the Keil IDE: open the `.uvprojx` file and press F7. The `.vscode/tasks.json` contains task definitions for building via `uVision.com` CLI, but the project paths there reference `project/arm/project.uvprojx` which is stale — they may need adjustment to point to `MDK-ARM/stm32f401ccu6.uvprojx`.

## Architecture

### Layer model

```
user/app.c                          ← application logic (setup/loop)
user/drivers/inc/dac8563.h          ← DAC8563 driver header
user/drivers/src/dac8563.c          ← DAC8563 driver (SPI write, init, waveform tables)
user/config/serial_config.c         ← serial instance wiring (serial0 + serial6)
user/platform.h                     ← pulls in STM32 HAL headers
─── boundary ───
zzy_new_lib/serial/                 ← shared MCU-agnostic serial framework
zzy_new_lib/common/                 ← critical sections, delays
─── boundary ───
Core/Src/*.c                        ← CubeMX-generated HAL init (main, spi, gpio, usart, it)
Drivers/STM32F4xx_HAL_Driver/       ← vendor HAL (do not modify)
Drivers/CMSIS/                      ← CMSIS core + device headers (do not modify)
```

### How code is organized across layers

**`Core/` — CubeMX-generated HAL initialization.** This is the standard STM32CubeMX output. `main.c` calls `HAL_Init()` → `SystemClock_Config()` → `MX_GPIO_Init()` → `MX_USART1_UART_Init()` → `MX_SPI1_Init()` → `MX_USART6_UART_Init()`, then enters the `setup()`/`loop()` pattern. All `Core/` files between `USER CODE BEGIN/END` markers are regenerated by CubeMX; edits outside markers are lost on re-generation.

**`user/` — Application code (not overwritten by CubeMX).**
- `app.c` — Laser galvanometer firmware. `setup()` inits both serial instances (USART1 echo, USART6 laser commands), initializes the DAC8563, and seeds a default circle task. `loop()` executes the task queue, dispatching to `draw_circle()` (36-segment interpolation) or `draw_rectangle()` (4-corner), and swaps in new tasks when received via USART6.
- `global_head.h` — Single include for all app code; pulls in the shared library (`common/common.h`, `serial/serial.h`) plus `main.h`, `serial_config.h`. Defines `GPIO_FAST_SETBIT`/`GPIO_FAST_RESETBIT` macros (BSRR register access) and declares `extern SPI_HandleTypeDef hspi1`.
- `platform.h` — Includes `stm32f4xx_hal.h`. Satisfies the `zzy_new_lib`'s requirement that every project provides its own `platform.h`.
- `config/serial_config.c` — Defines `serial0` (USART1 PA9/PA10, debug echo) and `serial6` (USART6 PA11/PA12, laser command input) at 115200 baud. Each has TX ring buffer (512B), RX dual-buffer pool (2×256B), and ISR handler.
- `drivers/inc/dac8563.h` — DAC8563 register command defines, pin macros (SYNC/LDAC/CLR via fast GPIO), function prototypes, wave table externs.
- `drivers/src/dac8563.c` — DAC8563 driver: hardware SPI write via direct `SPI1->DR` register access (avoids HAL overhead for low-jitter galvo timing), init sequence (reset → power-up → internal ref enable → gain=2), output functions for uint16/int16/float, and pre-computed sine/triangle wave tables (255 entries each).

**External shared library (`c:\projects\mcu\usr\zzy_new_lib\`).** A reusable, MCU-agnostic embedded C library providing:
- `serial/` — Three-layer serial driver: core (`serial.c` — ISR-driven TX ring buffer, RX with idle-line detection, buffer pool manager, event callbacks), port (`serial/ports/stm32f4/` — vtable impl for STM32F4), config (app-provided `serial_t` instances with pin/baud/buffer config).
- `common/` — `enter_critical()`/`exit_critical()` (nesting-aware), `delay_us()`/`delay_ms()`.
- `data_structure/ring_buf/` — Standalone ring buffer utility.

All allocation in the shared library is static — no heap usage.

### Key design patterns

- **setup()/loop()** — `main.c` calls `setup()` once after peripheral init, then `loop()` in the infinite while. All application code goes in these functions; nothing goes directly in `main()` USER CODE blocks.
- **Dual USART** — USART1 (`serial0`) handles debug echo via `serial_event_cb`. USART6 (`serial6`) receives laser control commands via `uart6_callback` using semicolon-delimited protocol (`U;` for update, `0C,x,y,r;` for circle, `1R,x,y,l,h;` for rectangle). Both are driven by the `zzy_new_lib` serial framework, bypassing HAL UART handles.
- **Task buffer double-buffering** — `task_buf[]` is the active queue (executed in `loop()`), `task_buf_1[]` receives new tasks from USART6 commands. When `flag_update` is set (triggered by `U` token in serial input), the buffers are swapped via `memcpy` → `memset`. This prevents partial updates during drawing.
- **CubeMX USER CODE regions** — Code between `USER CODE BEGIN/END` markers in `Core/` files survives CubeMX re-generation. All other content in those files is regenerated.
- **SPI1 TX-only simplex** — SPI1 is configured as master TX-only (no MISO pin). This is correct for the DAC8563 which is write-only over SPI.
- **Direct SPI register access** — `dac8563_write()` writes `SPI1->DR` directly with busy-wait on `SPI_FLAG_BSY`, avoiding HAL's `HAL_SPI_Transmit()` overhead. This minimizes jitter for laser galvo interpolation timing.

## SPI1 Configuration (for DAC8563)

- Mode: Master, 2-line TX-only simplex unidirectional
- Data size: 8-bit
- CPOL=Low, CPHA=1st edge (SPI mode 0)
- NSS: Software-managed (PA4 = DAC8563_SYNC)
- Baud rate prescaler: ÷2 → 42 Mbps from 84 MHz APB2
- No CRC, no TI mode

## Serial Framework Design Notes

The custom serial framework (`zzy_new_lib`) replaces the HAL UART API entirely. To work with serial in this project:

- **Receiving:** Call `serial_recv_to_idle()` to receive until an idle line condition. The callback fires `SERIAL_EVT_RX_DONE` with a borrowed buffer — you must call `serial_buf_return()` after processing, then re-arm with another `serial_recv_to_idle()`.
- **Sending:** `serial_send()` queues data to the TX ring buffer. The ISR drains it. `SERIAL_EVT_TX_DONE` fires when the full transmission completes.
- **Callback context:** Event callbacks run in ISR context — keep them short. Current echo implementation directly sends from the RX callback, which is acceptable for short echo loops.
- **Buffer pool:** When calling `serial_recv*(buf=NULL, ...)`, the framework allocates from the RX buffer pool. The `serial_recv_supply_buf()` API enables zero-gap ping-pong receive for high-throughput scenarios.
- **Critical sections:** `enter_critical()`/`exit_critical()` are nesting-safe — used internally by the serial framework. If you access `serial_t` fields from application code, wrap with critical sections.

## Laser Command Protocol (USART6)

Commands are semicolon-delimited ASCII, parsed in `uart6_callback()`:

| Token | Meaning |
|-------|---------|
| `U` | Trigger task buffer swap (`flag_update = 1`) |
| `0C,x,y,r` | Slot 0: Circle at (x,y) with radius r |
| `1R,x,y,l,h` | Slot 1: Rectangle at (x,y) with length l, height h |
| ...up to slot 9 | Same pattern for slots 2-9 |

Example: `U;0C,0,0,5000;1R,-2000,3000,4000,2000;` — draws a circle at origin (r=5000) then a rectangle.

**Important:** The callback runs in ISR context. `strtok`/`sscanf`/`memcpy` execute inside the interrupt — keep command frames reasonably sized (pool buffer max is 256 bytes).
